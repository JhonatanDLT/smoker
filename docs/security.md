# Security

## What pgproof touches

| System | Access | Why |
|---|---|---|
| Source database | Read-only metadata (`pg_catalog`) and a sample for profiles | Introspection and distributions |
| Target database | Truncate, write, update during repairs | Generate the dataset |
| Local disk | Reports, catalog, plan and profile JSON | Artifacts |

Nothing else. There is no server, no telemetry and no outbound network call
during a run.

## DSNs

- Read from environment variables by default.
- `--dsn` is supported but discouraged: the command line is copied into the
  report's `reproduce` field.
- The CLI never prints the DSN.
- The report never contains the DSN.
- In CI, pass it from secrets and use `--source-env` / `--target-env`, so the
  argument list contains the variable name, not the value.

If a DSN leaks:

1. Rotate the database password.
2. Revoke the role or token.
3. Check the CI logs and the report artifacts.
4. Audit connections from the leaked host.

## Profiles and PII

`pgproof profile` stores:

- Null fraction, distinct count and histograms (aggregates).
- Top values for low-cardinality columns (raw values).

Top values can contain names, emails, RFC, phone numbers or addresses. Treat the
profile file as sensitive:

- Use `--no-values` for schemas with personal data.
- Keep `profile.json` out of public repositories.
- Delete profiles you no longer use.
- Do not use a profile as a benchmark or training dataset.

## Generated data

The output is synthetic. It does not copy source values, except:

- Categorical top values sampled from the profile (for example a status enum).
- Semantic values generated by name (emails, names, RFC-like strings).

These are not real records, but a categorical value copied from production can
still be sensitive. If that matters, use `--no-values`.

## Target safety

- pgproof truncates the target tables in the plan before writing. This is
  destructive by design.
- Never point the target at production.
- The CLI warns when source and target are the same database.
- The GitHub Action refuses the same database unless `allow-same-db: true`.
- `TRUNCATE ... CASCADE` can affect tables that reference the target but are not
  in the plan.

## Least privilege

Source role:

```sql
GRANT CONNECT ON DATABASE app TO pgproof_reader;
GRANT USAGE ON SCHEMA public TO pgproof_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO pgproof_reader;
```

Target role needs `TRUNCATE`, `INSERT`, `UPDATE` and sequence usage.

Do not use a superuser. If a trigger requires elevated privileges, run it in a
dedicated environment.

## Transport

- Use `sslmode=verify-full` in production DSNs.
- Prefer a private network or an SSH tunnel for the source.
- Do not disable TLS verification to "make it work".

## Telemetry

There is none. The CLI does not phone home, does not send usage data and does
not check for updates.

## Artifacts

A report contains:

- Schema metadata (table and column names, constraints).
- Synthetic sample rows for failures.
- Hashes and counts.

It does not contain source rows, DSNs or credentials. Still, schema names can be
confidential: treat `report.json`, `catalog.json` and `plan.json` as internal.

## Incident checklist

- [ ] Rotate credentials.
- [ ] Delete leaked artifacts.
- [ ] Check who accessed the database.
- [ ] Review CI secrets and logs.
- [ ] Document the incident and the fix.
